# fastapi_vision_server

## Industrial Vision API

A FastAPI backend for industrial machine-vision systems, defect detection, and PLC automation.

## Documentation

Swagger UI and ReDoc are disabled by default. Enable `DEBUG=true` in `.env` only during local development to expose `/docs` and `/redoc`.

For scoped API key setup and the YOLO annotated stream endpoint, see [API_KEY_QUICKSTART.md](API_KEY_QUICKSTART.md).

---

## Features

- **Camera HAL**: USB (DirectShow/UVC), RTSP IP (low-latency TCP), and GigE Vision / USB3 Vision industrial cameras with hardware or software trigger (optional install; not yet run on a real camera, see [the real-life tests](docs/real-life-tests/triggered-cameras.md))
- **AI Inference Engine**: YOLO ONNX inference through ONNX Runtime; GPU providers depend on platform-specific runtime installation
- **QR & 1D/2D Barcode Engine**: Instant decoding and SKU verification
- **Rule, Action & Flow Engines**: Asynchronous decision logic for configured PLC outputs and MQTT alerts
- **Industrial Protocols**: Modbus TCP, Siemens S7, EtherNet/IP, OPC UA, generic configured TCP frames, and MQTT IoT Telemetry; OPC UA channels can scan a private IPv4 subnet and currently connect through None-security endpoints
- **Live Stream Monitoring**: Real-time WebSockets with live annotated bounding boxes
- **Database & Auth**: SQLAlchemy Async ORM with Alembic migrations & JWT authentication
- **Sparkplug B**: each production line published as a device of a Sparkplug B edge node, for Ignition and other SCADA hosts, with optional start/stop and counter-reset commands
- **Production records**: every product and code read stored in the database, a Records page with filters and totals, and CSV / Excel (.xlsx) export for any time range; line counters survive a restart
- **Inputs**: the PLC can start and stop a line, count its products with a sensor or its own counter, trigger a picture, reset the counters, set the batch number, confirm a reject and raise an alarm; a vision camera can inspect one picture per trigger, for parts that stand still
- **Production Lines**: several independent lines on one server, each with up to eight cameras (vision or QR reader) set up as cards on Line setup, its own counters and output actions, sharing the PLC, MQTT, TCP and webhook channels

## Quick Start

```bash
# 1. Activate virtual environment
.venv\Scripts\activate          # Windows
source .venv/bin/activate       # Linux/macOS

# 2. Copy .env.example to .env and set unique SECRET_KEY and ADMIN_INITIAL_PASSWORD values
#    SECRET_KEY must be at least 32 characters; initial admin password at least 20.

# 3. Run from the project directory
uvicorn main:app

# 4. Sign in to the dashboard using the initial admin password configured in .env
#    http://localhost:8000/dashboard
```

### Docker Compose (Linux, production)

One container, `vision`, runs the server under a small supervisor (`docker/supervise.py`). Set up once:

```bash
cp .env.example .env          # set SECRET_KEY and ADMIN_INITIAL_PASSWORD (and TZ); never commit it
sudo systemctl enable docker  # start Docker, and with it the server, on every boot
```

| Task | Command |
| --- | --- |
| Build | `docker compose build` |
| Start | `docker compose up -d` |
| Status (shows `healthy` once the server answers) | `docker compose ps` |
| Follow the logs | `docker compose logs -f` |
| Restart | `docker compose restart` |
| Stop and remove the container (data is kept) | `docker compose down` |
| Rebuild and restart after a code change | `docker compose up -d --build` |
| Health and restart count | `docker inspect --format '{{.State.Health.Status}} restarts={{.RestartCount}}' $(docker compose ps -q vision)` |
| Health report | `curl http://localhost:8000/health` |

**Updating safely.** `git pull`, then `docker compose up -d --build`. The volumes are reused and database migrations run on start; the first start of a new major version writes `*.v1-backup.*` copies of the database and settings first. Never add `-v` to `docker compose down` unless you mean to delete all data. Before an update, a backup is one command while the server is stopped (`docker compose stop`):

```bash
docker run --rm -v vision-server_vision-data:/data -v "$PWD":/backup alpine tar czf /backup/vision-data.tgz -C /data .
```

**What survives what.** Everything the server writes is on a named volume; the rest of the container is read-only.

| Volume (path in the container) | Holds | Restart | `down` / `up` | Rebuild | Host reboot | `down -v` |
| --- | --- | --- | --- | --- | --- | --- |
| `vision-data` (`/app/data`) | SQLite database, saved settings, v1 backups | kept | kept | kept | kept | deleted |
| `vision-models` (`/app/model_store`) | uploaded and OTA models | kept | kept | kept | kept | deleted |
| `vision-certs` (`/app/certs`) | MQTT TLS certificates and keys | kept | kept | kept | kept | deleted |
| `vision-uploads` (`/app/uploads`) | uploads; `.tmp` holds uploads in progress and is emptied on every start | kept | kept | kept | kept | deleted |
| `vision-logs` (`/app/logs`) | `app.log`, rotated at 10 MB, 5 old files kept | kept | kept | kept | kept | deleted |
| `/tmp` (memory, 64 MB) | scratch files | emptied | emptied | emptied | emptied | emptied |

The database runs in SQLite's WAL mode, so copy it only while the server is stopped (or copy the `-wal` file with it), and keep it on a local disk or Docker volume, not a network share.

**Recovery.**
- A crash, a fatal Python error, or the kernel ending the process at the memory limit (`VISION_MEM_LIMIT`) ends the container, and `restart: unless-stopped` starts it again. Docker waits longer between attempts while it keeps failing right after starting.
- A server that hangs (still running, no longer answering `/health`) is stopped by the supervisor after `WATCHDOG_FAILURES` failed checks, and then restarted. Docker's healthcheck alone only marks a container unhealthy; it never restarts it. While the server is still starting (its port not yet open), failed checks do not count, for up to `WATCHDOG_STARTUP_TIMEOUT`.
- Background threads (camera readers, inference, video, QR readers) that crash are logged with their traceback and restarted in place; `worker_restarts_total` in `/api/v1/telemetry/metrics` counts them.
- Cameras, the MQTT broker and PLCs may be off when the server starts. It waits at most `STARTUP_CONNECT_WAIT_SECONDS` for them, then serves the API while they connect in the background. A camera that could not be opened is retried with growing pauses (up to `CAMERA_RECONNECT_MAX_SECONDS`); a stream that drops is reopened the same way. Each MQTT channel has its own broker connection and reconnects on its own (1 s, doubling up to 60 s). PLC connections are retried on the next operation, with the fail-safe watchdog raising alarms meanwhile.
- The Line dashboard's **Alarms** panel lists the line's active alarms and those every line shares (PLC connection, inference, flows), with severity, since when, how often it repeated and who acknowledged it; **Cleared** shows the recently cleared ones. **Acknowledge** (any signed-in user) records that someone has seen an alarm; it stays listed until its cause is gone. The alarm count next to the line state counts the same alarms and opens the panel. `GET /api/v1/alarms?line_id=…&include_all_lines=true` gives the same list.
- Alarms clear themselves once their cause is gone: flow alarms on the node's or flow's next clean run (or when the flow is changed or deleted), the overload alarm once the backlog halves, a PLC that did not disconnect cleanly on its next connect, and an output action's failure alarm when the action is deleted or switched off. `GET /api/v1/alarms/catalog` lists every kind of alarm with its label and whether it belongs to one line or to all.
- `/health` answers from memory and never runs inference or touches a camera. It returns 503 only when the database is down; a camera or PLC fault shows as `degraded` with status 200, so a cable fault does not restart the server.

**Stopping.** `docker compose stop` (or `down`, a host shutdown or a Docker restart) sends SIGTERM and allows 60 s. Open video streams close at once, queued PLC operations finish, every PLC output with a safe state goes to it (all PLCs at once), then telemetry, MQTT, cameras and the database are closed.

**Security.** Unprivileged user (uid 10001), read-only root filesystem, all Linux capabilities dropped, `no-new-privileges`, memory and process-count limits, no `.env` or keys in the image (`.env` is read at start). Only the HTTP port is published; `VISION_BIND_ADDRESS` limits it to one network card. Passwords in camera URLs and tokens are masked in the logs. The API is plain HTTP for the local network; its accounts and API keys are what protect it.

**Accounts and the dashboard.** A new account's password, and a changed one, must be at least 6 characters (the first admin password in `.env` at least 20). The dashboard page is served only to this machine and to private-network addresses, judged by the connecting address alone. Every page carries a Content-Security-Policy that lets scripts, styles, fonts and requests come only from this server, so a script injected into a page could not load code from elsewhere or send a sign-in token away. `DEBUG` is off unless `.env` sets it (with it on, `/docs` and `/openapi.json` are public).

**Hardware.** A container only gets the hardware it is given when it is created, so the machine is checked on the host, before the container starts:

```bash
python3 docker/detect_hardware.py --up    # Windows: python docker\detect_hardware.py --up
```

The script writes `docker-compose.override.yml` for this machine (Compose reads it together with `docker-compose.yml`; it is not committed), then builds and starts. The usual `docker compose` commands use the hardware from then on. Run it again after adding or removing hardware: the container does not start while a GPU or device listed in the file is missing. `--dry-run` only prints what it found, and deleting the file goes back to the plain CPU setup.

| Host | Inference | USB cameras, serial adapters |
| --- | --- | --- |
| Linux PC (x86-64), NVIDIA GPU, NVIDIA Container Toolkit installed | GPU (CUDA) | passed in |
| Windows PC, NVIDIA GPU, Docker Desktop | GPU (CUDA) | cannot be passed in |
| Jetson, Raspberry Pi and other arm64 boards | CPU | passed in |
| Anything else | CPU | passed in on Linux only |

- *NVIDIA GPU.* The script builds the image with `ACCEL=nvidia` (ONNX Runtime's CUDA build plus CUDA and cuDNN, which makes it several GB larger) and reserves the GPU for the container. If the GPU cannot be initialised at run time, ONNX Runtime logs the error and the model runs on the CPU. Tested on Windows 11 with Docker Desktop and a GTX 1650 (a YOLO26s model at 36 ms per frame, against 244 ms on that machine's CPU); not yet tried on a Linux host.
- *Linux, USB cameras and RS-485 adapters.* The script passes in every `/dev/video*`, `/dev/ttyUSB*` and `/dev/ttyACM*` with the group that owns it; listing them by hand under `devices:` and `group_add:` in `docker-compose.yml` works too. A listed device that is missing stops the container from starting. A USB camera that stops delivering frames (unplugged and plugged back in, for example) is reopened; this has been tested with a simulated device only.
- *Host network.* The discovery beacon (UDP 8888) and some PLC or camera setups need the host's own address; remove `ports:` and uncomment `network_mode: host`.
- *Windows and macOS (Docker Desktop).* Runs as is with IP cameras and network PLCs; keep the named volumes (a bind mount of a Windows folder can refuse SQLite's WAL mode). USB cameras and serial ports cannot be passed into the container there; run the server natively (`start_server.bat`) for those.
- *NVIDIA Jetson and other arm64 boards.* The script recognises a Jetson, passes its cameras and serial adapters in and builds the CPU image. The arm64 image has been built and has run a model under emulation on a PC, not on a real board. For the GPU on a Jetson, build on NVIDIA's L4T/JetPack base image with the ONNX Runtime GPU wheel for that JetPack version, add `runtime: nvidia` to the service (with the NVIDIA container runtime installed) and set `INFERENCE_DEVICE=auto`. This is not part of this image and has not been tested. The original Jetson Nano (JetPack 4, Python 3.6, CUDA 10.2) has no ONNX Runtime GPU build for the Python and package versions this server uses, so it can only run inference on the CPU.

**MQTT broker (optional).** A site with no MQTT broker gets a Mosquitto beside the server:

```bash
# .env: set BROKER_PASSWORD (and BROKER_USERNAME, vision by default)
docker compose --profile broker up -d
```

Without `--profile broker` it is not started, and an existing deployment does not change. Every client signs in with the one login from `.env` (the password file is written from it on every start); the broker does not start while `BROKER_PASSWORD` is empty. Under Connections, add an MQTT channel with host `mqtt`, port 1883 and that login; Ignition and other devices use this machine's address and `BROKER_PORT` (1883 by default; `BROKER_BIND_ADDRESS` limits it to one network card). Its retained messages are on the `vision-broker` volume. It has no TLS: keep it on the plant network. This service has not been started under Docker yet (its configuration was run with a local Mosquitto): watch `docker compose logs mqtt` on the first start.

### Production lines (version 2)

One server runs several production lines. Each line has up to eight cameras, each with its own count lines and classes, its own counters, send cards, output actions and inputs, and runs on its own; the connections set up on the Connections page are shared by every line. Only Supervisor and Admin accounts can change lines and product codes; every user sees every line.

**Upgrading from version 1.** On the first start the server copies `data/system_state.json` to `data/system_state.v1-backup.json` and the SQLite database to `*.v1-backup.db`, adds an empty `products` table, and turns the current setup into **Line 1** (same settings, active camera and PLC cards). Line 1 keeps its settings in the old keys, so every existing API call and the dashboard answer for Line 1 when no line is named. To go back, export the product list if you need it, put the database backup back in place and start version 1; it runs Line 1 and ignores the other lines.

**Later upgrades.** The settings file carries a `schema_version`; a newer server upgrades it once on its first start, so a line keeps doing what it did: the two "connect on start" switches became the one on the Cameras page, the product codes became **List 1** (every code reader stays set to it), each line's "send results" settings became send cards that send the same messages, each vision camera got the model and the class lists its line used (see **AI models** below), each send card on an MQTT channel got the topic that channel published to, each vision camera keeps rejecting classes named like a defect and got its line's count lines (see **Counting** below; the line keeps them too, for version 1 and older API clients), and each TCP channel is set to what it really sent (a newline after each message, as a client), since its delimiter and mode were not used before. **Version 9** (codes read Continuously are only shown): the upgrade flags each camera that reads codes Continuously, since its reads no longer reach the line; it does not choose a trigger for it, because whether a picture on a wire line catches the code depends on where the camera sits. Line setup opens such a camera on its **Codes** with a red note, and the running line raises the alarm *Codes only shown*, which says what the line does meanwhile: with Sync on it uses **When no code is read** (*Reject* rejects every product), and a line with only a reader that checks codes counts nothing. Choose a wire line or *When an input asks*, or press **Keep show only** (offered when the camera checks no codes and Sync does not depend on it).

**Setting up a line** (dashboard, Supervisor or Admin):

1. **Lines** → enter a name → **Add line**. A new line starts stopped and without cameras. **Clone** copies a line's logic and output actions, but not its cameras or its inputs (two lines would be started and stopped by the same bit); a copied output action therefore has no camera and no confirmation signal until you pick them again.
2. Pick the line in the header's **Line** selector and open **Line setup**. At the top are the line's own settings (name, **Minimum processed frames/s**, **Yield target**, **Sync**), **Save line setup**, **Start/Stop line** and **Reset counts…**. Below, each camera of the line is a **card**, and each card holds every setting of that camera; nothing is set on another page. A line has **up to 8 cameras** (and never more than `MAX_CONNECTED_CAMERAS`, the most the server connects at once).
   - **Add camera** (the last card): pick a camera that belongs to no line (cameras on another line are greyed out with its name), or **Scan USB**, or **Add network camera** (name and RTSP/HTTP URL: the same as an *IP Camera* under Connections). Then choose its **starting job** and **Add camera**. The first vision camera is the counting camera.
   - A card's header shows the camera's name, its job, a dot (green: connected) and a small live picture (about one a second, only while Line setup is open). The arrows change the camera order and **×** removes the camera from the line (it stays on the Cameras page). The card's sections fold open and closed; each browser remembers which were open, per camera. Only the sections for the camera's job are shown:
     - **Camera**: the device (change it here), its name (renames it everywhere), **Connect** / **Disconnect**.
     - **Job**: *Counting* (the line totals come from it; a line with a vision camera has exactly one, and choosing *Counting* on another card makes the previous one an own inspection station), *Inspection station* (counts and rejects on its own and only fires the PLC and send cards that name it), *Code reader*, *Counting + code reader* or *Inspection station + code reader*. An inspection station is an **Own station** (it counts on its own, as above) or **Joins the product result** (its result is merged into the counting camera's product; see *Several cameras on one product* below), with its **Travel time from the counting camera**, **Match window** and **When no result**.
     - **AI model and classes** (vision jobs): the **Vision model** (the models uploaded on the AI models page), whether it is loaded, and two lists filled from the model's own class names: **Products to count** and **Defects to reject**. A line cannot be saved with a vision camera that has no model. With nothing ticked in either list, every class the model finds counts as a product. **Confidence threshold** (0.05 to 0.99; empty = the model's own) drops weaker detections on this camera. **Also reject classes whose name contains "defect", "scratch" or "broken"**: on for cameras set up before this switch existed (so they keep rejecting what they rejected), off for cards added now.
     - **Counting** (vision jobs): the **Count mode**, *Moving products cross count lines* (the default) or *One picture per trigger* (parts that stand still; the fields below are then hidden and **When nothing is found** is shown, see *Trigger inspection* below). For moving products: the **Flow direction** (top → bottom, bottom → top, left → right or right → left), **Count crossings** (*A then B*, the flow above, or *Both ways*), and **Count lines A and B**, as numbers (0 to 1 across the picture) and as two lines drawn on the camera's picture that you can drag. **Advanced tracking** has the tracker's settings (min hits, missed frames, max speed, match threshold, position tolerance, high and low confidence); an empty box uses the default shown in grey. A counted product is left alone while it moves out of the picture on the side its flow leads to (with *Both ways* there is no such band), whatever the camera's rotation. A class counts as a defect when it is ticked under **Defects to reject** (or, with the switch above on, by its name).
     - **Codes** (code reader jobs): below.
     - **Image**: width, height, FPS, rotation, flips, the **ROI** (drag on the camera's whole picture to draw it; only that part goes to the AI model, the code reader and the video; it is taken after resizing, rotation and flipping), and the USB image controls or the IP transport and buffer.
     - **Video**: **Max stream width** and **JPEG quality** of the camera's live video.
   - **Save line setup** saves the line and every card at once, then the image and video settings of each camera that changed. Leaving the line with unsaved changes asks first. On the Cameras page, **Settings** of a camera that belongs to a line opens its card here; a camera on no line keeps the Settings window there.
   - A vision camera with *+ code reader* decodes codes too, on its own thread beside the model, with the same **Read codes** choices as a code reader: one camera can count products and read their codes. Its reads show under **Latest code reads** on the Line dashboard (with **Test picture**), are outlined on its AI view, and go out like a code reader's.
   - *Code reader*: reads QR codes, Data Matrix and 1D barcodes (with zxing-cpp) and checks each code against **Products**. **Read codes** sets when:
     - *Continuously (show only)*: every frame, and the codes are **only shown**: outlined on the camera's picture and listed under **Latest code reads** (tagged *shown only*), once until they have been out of view for the camera's hold time. Nothing else: they pair with no product, fire no card, send no message and make no record. Use it to aim and check a camera. To use the codes, choose one of the two choices below. A camera that checks codes (*Accept only listed codes*, *Reject listed codes*) cannot be saved on it, and Sync needs a camera that reads on a wire line or when an input asks.
     - *One picture when a product crosses wire line 1* (or *2*): the counting camera triggers the QR camera, which takes one picture after the **picture delay** (the time the product needs to reach it) and decodes it. The picture shows on the Line dashboard with each code boxed, green for known products and red for unknown ones. A picture without a code is a *no read* (and fires *No code read* cards) even without Sync; before that, the next two frames are tried (within 0.4 s). **Test picture** on the dashboard takes one on demand to check aim and focus; it sends nothing.
     - *When an input asks*: one picture each time an input with the action *Take a picture* fires whose trigger is ticked on this camera's card (see *Trigger numbers* below), after the **picture delay**. Use it where the PLC knows when the product is in front of the reader, and on a line whose counting camera takes one picture per trigger: that camera tracks nothing, so no product crosses a wire line there and the two choices above are greyed out.
     - A frame where nothing reads gets a second pass: code-like areas are sharpened and deblurred for straight motion blur of 3 to 15 px along or across the picture (40 ms per frame when reading continuously, 150 ms for a single picture). It reads codes smeared by a moving conveyor that the first pass misses, but a short exposure (fast shutter, more light) is still the real fix: the code should move well under the size of one of its squares while the picture is taken. While nothing reads, a continuously reading camera tries the second pass at most ten times a second.
     - A camera reads codes only with a code reader job, and only while its line is running.
   - A camera that reads codes also has an **Action**, a **Product list** and **When no code is read**:
     - *Report only* (the default): the code is shown and can fire code triggers; the product count is not changed.
     - *Accept only listed codes*: a product whose code is not in the camera's product list is rejected.
     - *Reject listed codes*: a product whose code is in the list is rejected.
     - With one of the two checks, a product gets **one result, decided once**: it is good only when the vision camera found it good and its code passed. The line holds the product until its code arrives or the Sync window ends, then counts it and fires the cards once. Sync is switched on for this. *When no code is read* says what happens to a product without a code: *Reject*, or *Ignore* (the vision camera alone decides). A reject by code counts and fires reject cards exactly like a reject by the vision camera, and a reject card's travel delay runs from the moment the product crossed the count line, so it must be longer than the Sync window (Line setup warns when it is not).
     - On a line with only a reader and no vision camera, the code alone decides: each picture an input asks for (*When an input asks*) is one product, good or reject. With a *Product sensor* signal on such a line (see *Inputs*), the sensor is the product: a code read is no longer a product of its own, and Sync pairs each sensor product with its code.
   - **Sync** (one vision camera and one code reader looking at the same spot, or one vision camera that also reads codes): each counted product goes out with the code read inside the sync window around its crossing; a picture taken on a wire line crossing pairs only with the product that triggered it. A product without a code goes out as *no read*; a code without a product goes out *unpaired*. Products must pass further apart than the window, and a reject card's travel delay must be longer than it. Sync needs a vision camera (or a PLC product sensor) and a camera that reads codes: when the line's cards no longer have both (the cameras were removed), Line setup switches Sync off and greys it out, so the line can still be saved, and switches it on again when they are back.
   - **Minimum processed frames/s**: the line raises an alarm when it falls below this.
   - **Yield target (%)**: the Line dashboard marks the yield as below target under this value; 0 means no target.
3. Set the send cards and the output actions below the camera cards. **Send results** works like output actions: add a card, pick the one MQTT, TCP or webhook channel it sends to, its trigger and condition, and what the message contains (or the whole message). An MQTT channel is the broker (address, login, TLS, MQTT 3.1.1 or 5, QoS and retain) and the card names the **topic**, so several cards can publish to different topics on one broker, and two MQTT channels can be two brokers at once. For a plant broker reached by IP address over TLS, upload its CA certificate and enter the name on the broker's certificate as the server name; **Test message** sends it once with example values, and **Apply** saves the cards. To report to two systems, add two cards. A send card has no delay: the message goes out as soon as the product's result is known. PLC cards and send cards share the same triggers and the same check on the server, and *good* and *rejected* mean the product's final result. Cards gain the triggers *QR code read*, *Known code*, *Unknown code* and *No code read (Sync)*, and an optional camera. The *Line started / stopped* trigger fires when the line is started or stopped (from the dashboard or the API), with the conditions *On* (starts), *Off* (stops) or *Toggled* (either), for example to switch a tower light. The *Alarm raised / cleared* trigger fires on the alarms ticked in the card's list (or *Any alarm*), with the conditions *Raised* (a ticked alarm goes on), *Cleared* (none of them is on any more) or either; for a lamp, use one card that sets the output on *Raised* and one that resets it on *Cleared*. Camera, frame-rate and output action alarms fire only their own line's cards; PLC connection, inference and flow alarms fire every line's. **Send cards only** have the *Timer (every N ms)* trigger: the card sends the line's state and totals (event `TIMER`, the line, its state, batch, counts and metrics) every interval, set in **Value / class** in ms (100 to 86,400,000, that is up to 24 hours; 1000 by default), with the conditions *While the line runs* (the first message one interval after the line starts; nothing while it is stopped) or *Always (continuous)* (also while the line is stopped). A timer that falls behind on a busy server skips the messages it missed rather than sending them at once; it uses no camera. **Cards / List** above the output actions switches how they are shown. When two lines write the same PLC address, the Lines page lists it as a warning.
   - **Text messages.** A send card's **Message format** is *JSON* (the fields it picks, as before) or *Text*: a template you type, for a label printer, a display or an older PLC that reads plain text. `{name}` is replaced by its value, for example `{result_code};{class_name};{code}`; a value the event does not have is left empty. `{{` and `}}` write a brace, and `\r`, `\n` and `\t` a carriage return, a newline and a tab. The values are `line_id`, `line_name`, `line_state`, `event`, `timestamp`, `date` and `time` (the server's local time), `camera_id`, `camera_name`, `track_id`, `class_name`, `confidence`, `result`, `result_code` (1 good, 2 reject), `reject_reason`, `reject_camera` (the camera whose result rejected the product), `code`, `code_format`, `code_status`, `product_name`, `product_id` (the product ID the code holds; the code itself for a list that reads whole codes), `good_count`, `rejected_count`, `total_inspected`, `yield_percentage`, `products_per_minute`, `batch` (the item's batch from its code, else the line's batch number; empty while there is none), `alarm_code` and `alarm_message`; clicking one in the dialog puts it in the text. A name that is not in this list is refused when the card is saved. The text goes out as it is: over TCP followed by the channel's delimiter, over MQTT as the payload, and to a webhook with `Content-Type: text/plain; charset=utf-8` unless the channel's own headers set a Content-Type.
   - **TCP channels** (Connections) now do what their settings say. **End of each message** is the delimiter written after each message: `\n`, `\r\n`, `\0`, none, or **Custom** (text where `\n`, `\r`, `\t`, `\0`, `\\` and `\xHH`, a byte in hex such as `\x03`, stand for that character). **Timeout** is used for connecting and for writing. In **Client** mode the server connects to the device; as before, each message has its own connection, unless **Keep connection open** is on: then one connection carries every message, and after a failure the next message connects again, waiting 1 s, then twice as long each time up to 30 s, between tries. In **Server** mode the channel listens on its port (the host is the address to listen on, `0.0.0.0` for every network) and each message goes to every device connected to it; with none connected, a message is not sent and its card says *No device is connected*. The listener starts when the channel is saved and when the server starts, and stops when the channel is deleted. A kept connection that cannot reach its device, or a port that cannot be opened, raises the alarm **Message channel down** (`send.channel_down`) until a message goes out again. Messages from send cards, flows and phone scans all go out with the channel's settings.
   - **Output actions that write a value.** A *WRITE* action's **Value** is a *Fixed number* (as before) or a value of the product at the moment it is written: *Result code* (1 good, 2 reject), *Good count*, *Reject count*, *Total count*, *Class number* (the product's place in its camera's **Products to count** list followed by **Defects to reject**, from 1; 0 when it is in neither), *Reject reason code* (0 not rejected, 1 vision class, 2 code not in the list, 3 code in the reject list, 4 no code read, 5 a joined camera saw nothing, 6 nothing detected by a camera in trigger mode, 7 a product check, 8 no result in time (result handshake), 9 other, 10 no picture (a trigger got no picture)) or *Batch number* (the line's batch number, which must be a number here; while the line has no batch, or one that is not a number, such an action fails and says why). **Then pulse strobe address** pulses another address (for **Strobe pulse**, 10 to 10000 ms, 100 by default) after the value is written, with nothing else sent to that PLC in between, so the PLC knows a new value is there. A failed strobe fails the action and is not retried, so the PLC never sees two strobes for one value. **Test** writes example values: a rejected product, counts of 1, class 1, batch 1. The *Wait for PLC ACK / Reply* choice is gone: it never waited for anything. Actions saved with it work as before and report *sent*. To know that an action really happened, give it a **Confirmation signal**:
   - **Write any value.** A *WRITE* action can also write a value of the item it fires for:
     - *A field of the item's product* (`value_source` `product_field`, `value_field` the key): see *Product data*. Yes / no is written as 1 / 0.
     - *The code read* (`code`) or *the product's name* (`product_name`): text.
     - *The value of an input* (`input`, `value_input`): the last value an input of the line read. Give that input a **Value name** (`value_name` on the input: letters, digits and `_`, starting with a letter; not `value` or `previous`).
     - *A formula* (`formula`, at most 200 characters), worked out when the action fires, for example `if(result == "good", product.lane, 9)` or `round(input.speed / 4, 1)`. It uses numbers, text in double quotes, `true` and `false`; the values `result`, `result_code`, `reject_reason`, `class`, `confidence`, `code`, `code_status`, `product_id`, `good_count`, `reject_count`, `total_count`, `batch`, `line`, `camera`, `product.<field>` (and `product.name`, `product.code`, `product.list`) and `input.<value name>`; `+ - * / %`, `== != < <= > >=`, `and`, `or`, `not` and parentheses; and the functions `if(condition, a, b)`, `round(x)`, `round(x, digits)`, `min()`, `max()`, `abs()`, `int()` and `text()`. Text compares without regard to case; `+` joins two texts. `round()` rounds a half to the even number (`round(2.5)` is 2). A value that cannot be worked out (a missing value, a division by 0, an input that reads infinity) makes the whole formula's value missing; an input whose last read failed has no value either. **Check** in the dialog (`POST /api/v1/lines/{line_id}/formula/check`) says what is wrong and where, and warns about a field or input value the line does not have. The formula is never run as program code: it is read against a short list of what is allowed.
     - **If there is no value** (an unknown code, an empty field, an input not read yet, a formula that cannot be worked out, such as a division by 0): *Skip the write* (`if_missing` `skip`, the default; the card shows **Skipped**, and no alarm is raised) or *Write this value* (`default`, with `default_value`).
     - **Text** goes to an OPC UA String tag only, at most 254 characters (a number to a String tag is written as its text). Every other controller type refuses text: the action fails with "This controller type writes numbers only", and the dialog warns. An OPC UA tag of a number type refuses text too.
     - **Test** on such an action asks for a product code and writes that code's values (from the lists of the line's code readers; `"code"` in the body of `POST /api/v1/plc/actions/{id}/test`). With no code it tests with no product, so the action skips or writes its default.
   - **When-then rules.** Three ways to say when something happens:
     - **Input changed** is a trigger of output actions and send cards (`trigger` `input`, `input_id` an input of the line, `condition` `on` = off to on, `off` = on to off, `change` = any change). Every accepted change of that input fires it (after its debounce, whether the line runs or not, and whatever the input's own action does); the first value read after a start is not a change, and a PLC counter input sends none. The input action **Only fires cards** (`none`) is for an input that does nothing else; it may read text. A send card's message is `INPUT_CHANGED` with `input_id`, `input_name`, `value` and `previous`; a text message can use `{input_name}`, `{input.value}`, `{input.previous}` and `{input.<value name>}`.
     - **Only when** (`only_when`): up to 5 rules on any output action or send card (timer cards too), of which all or any (`match`) must pass, checked after the trigger and condition. A rule is a value name (`left`), an operator (`=`, `!=`, `<`, `<=`, `>`, `>=`, `contains`, `is empty`, `is not empty`) and a constant or another value name (`right`, `right_kind` `constant` or `value`). Numbers compare as numbers, yes / no as yes / no, and text without regard to case. A comparison needs a value to compare with (for "no value", use *is empty*). A rule whose value is missing does not pass, except *is empty*. Example: only when `product.lane = 3`.
     - **Product checks** (Line setup, `product_checks` of a line, up to 10): each has a name and Only-when rules, and rejects a product when they pass, for example *Wrong bottle*: `class` ≠ `product.expected_class`. They run for a product whose code is in a list (a product paired with its code, or a code read on a line whose reader checks codes), after every other reason, and see what is known before the result: their rules cannot use `result`, `result_code` or `reject_reason`. A check that cannot run (a damaged settings file) rejects nothing: the product is still counted. The reason is `product_check` (*product check*, reject reason code 7), and the message, the PLC event and the record carry the check's name as `product_check`. A line with checks pairs each product with its code (Sync), as a code check does.
     - A card that names an input its line does not have is refused, and so is deleting an input that a card names.
   - **Reject confirmation.** An output action can name a **Confirmation signal**: an input of the same line with the action *Confirm an output action*, for example a sensor that sees the rejected product leave the belt. After the action is sent (and its strobe pulsed), the line waits **Confirm within** (50 to 10000 ms, 1000 by default) for that signal. It comes: the action is *confirmed*. It does not: *not confirmed*, and the critical alarm **Output action not confirmed** (`plc.action_not_confirmed`) stays on until a later fire of that action is confirmed. Fires that wait at the same time are confirmed oldest first. A signal that comes while the output is still being pulsed counts. An action whose output failed waits for nothing, and **Test** does not wait. The action's card shows *Waits for a signal*, *Confirmed* or *Not confirmed*. A signal that an action names cannot be deleted or given another job until the action names another.
4. **Inputs**, below the output actions, let the PLC act on the line: start and stop it, count products, take a picture, set the batch number, confirm an output action or raise an alarm. See *Inputs* below. Skip this step when the PLC only receives.
5. **Start** the line. Its cameras connect without disconnecting other lines' cameras (at most `MAX_CONNECTED_CAMERAS`, default 8, across all lines). **Connect cameras when the server starts** on the Cameras page is the one switch for all lines: when it is on, the cameras of every running line are connected at startup (and retried in the background while they are offline). A camera that belongs to no line is connected by hand.

The **Line dashboard** shows the line's state, its **Batch** number (see *Batch number* below), yield and counts, the counting camera large and, beside it (below it on a phone), a **camera strip** with a small tile for each of the line's other cameras: its job, its own counts for an own station, *Joined* with its travel time and its **Matched** / **Unmatched** / **Rejects** / **No result** figures for a joined camera, and for a code reader the last picture or the live view with **Test picture**. Click a tile to show that camera large. Only the large camera is streamed; the tiles are still pictures refreshed one or two times a second. Video is only sent while the Line dashboard (or Plant overview with live tiles) is open and the browser tab is visible; it stops when you leave and resumes when you come back. Each camera's **Max stream width** and **JPEG quality** (its card's **Video** section) set the size of its video, and its **ROI** (the card's **Image** section) crops its picture before it reaches the AI model, the code reader and the video; the crop is drawn on the picture as the video shows it and keeps its own size. On the AI view, count line A (azure, *Entry*) and B (amber, *Count*) are drawn with arrows showing the flow between them, and line B flashes when a product is counted. The bar at the top of the video shows the line's counts, the video's frame rate and the model's time per picture (*YOLO*). It is drawn in proportion to the picture, so it looks the same size on screen whatever the camera's picture size or ROI; on a narrow picture its text goes on two or more lines rather than being cut off. **The cameras of a stopped line are shown but not inspected**: their bar starts with *LINE STOPPED*, has no *YOLO* time, and no boxes or codes are drawn (start the line to inspect). A camera on no line says *NOT ON A LINE*, and a camera whose model did not load says *NO MODEL*.

#### Several cameras on one product

A vision camera that is not the counting camera is an **Own station** (it counts and rejects on its own and fires only the PLC and send cards that name it; its products do not add to the line totals) or **Joins the product result**: it looks at the same products as the counting camera, before or after it on the belt, and each product gets **one** result from all of them.

- On the camera's card (**Job**, *Inspection station*, *Joins the product result*) set the **Travel time from the counting camera** (ms; negative when this camera is *before* the counting camera), the **Match window** (ms, 500 by default) and **When no result**: *Ignore* (the other cameras decide) or *Reject* (reason `station_no_result`, PLC reason code 5).
- A crossing of the joined camera at time *t* belongs to the product the counting camera saw at *t − travel time*, give or take the match window. A crossing that matches no product is dropped and counted as **Unmatched**. A joined camera counts nothing on its own.
- The product is rejected when the counting camera, **any** joined camera or the code check rejects it. The reason is the first of: the counting camera, the joined cameras in card order, the code, a joined camera that saw nothing. It is counted once and sends one event, when every camera has answered or the last match window has ended.
- The event carries `reject_camera_id` (the camera whose result rejected it) and `stations`, one entry per joined camera in card order: `{"camera_id", "camera_name", "result": "good" | "reject" | "no_result", "class_name", "confidence", "travel_ms"}` (`travel_ms`: how long after the counting camera it saw the product; use it to set the travel time). Pick **Joined cameras** and **Camera that rejected the product** in a send card, or `{reject_camera}` in a text message. A PLC or send card that names a joined camera fires for the products it takes part in.
- A reject gate's travel delay runs from the counting camera's crossing. Make it longer than the latest result (travel time + match window, and the Sync window with a code check); Line setup warns about an output action that is shorter. Products must pass further apart than twice the match window, or a crossing can be matched to the wrong product; while the line runs, Line setup warns when they do not.

*Example*: a top camera counts bottles and checks the caps; a side camera 400 ms further down the belt checks the labels. Set the top camera to **Counting** and the side camera to **Inspection station**, **Joins the product result**, travel time **400**, match window **150**, **When no result**: *Reject*. A bottle with a good cap and a torn label is rejected once (`reject_reason` `vision_class`, `reject_camera_id` the side camera); a bottle the side camera misses is rejected with `station_no_result`. The reject gate's travel delay must be more than 550 ms, and bottles must pass more than 300 ms apart.

#### Inputs

The PLC can send signals into a line. An **input** reads one address of a controller and says what the line does with it. The cards are on **Line setup**, under the output actions: **Add input**, fill in its window, **OK**, then **Apply**. A line has up to 32. A line without inputs works exactly as before.

| What the signal does | |
| --- | --- |
| *Start the line*, *Stop the line* | Starts or stops the line when the signal comes, as the dashboard's buttons do. |
| *Run the line while on* | The line runs while the value is on and stops when it goes off. |
| *Reset the counters* | Resets the line's counts. |
| *Product sensor* | Each signal is one product, on a line **without** a vision camera (with one, the counting camera counts, and a line is not saved with both). With a code reader and **Sync** on the line, the product is paired with its code and gets one result. The Line dashboard shows such a line as *Running* without a camera. |
| *Take a picture* | A trigger with a **trigger number**. One picture with every camera that has that trigger ticked on its card: a camera whose **Read codes** is *When an input asks*, or a vision camera whose **Count mode** is *One picture per trigger*. See *Trigger numbers* below. |
| *Set the batch number* | The value read becomes the line's batch number (see *Batch number* below). |
| *Confirm an output action* | Confirms the output actions that name this signal (see **Reject confirmation** above). |
| *Raise an alarm* | The alarm **Alarm from an input** (`plc.input_alarm`), with the card's own text and severity (info, warning or critical), is on while the value is on. Output actions and send cards with the *Alarm* trigger can react to it. |

- **controller** and **Address / tag**: a controller from Connections, and the address as its protocol writes it. Modbus: `C5` a coil, `10001` a discrete input, `R10` or `40011` a holding register, `30001` an input register. S7: `I0.0`, `M10.4`, `DB1.DBX0.0`, `MW10`, `DB1.DBD8`. EtherNet/IP: the tag's name. OPC UA: the tag's name (`Tag_1`, `DB1.Speed`) or its full NodeId. MELSEC: `M5`, `D100`. FINS: `CIO 0.05`, `D100`. A **Generic TCP channel cannot be read**: it only sends.
- **Read as**: *Auto* (the address's own type), *Bit*, *INT16*, *UINT16*, *INT32*, *REAL*, *Text* (only to set the batch number, from an OPC UA or EtherNet/IP channel) or *PLC counter* (only for a product sensor).
- **Act when the value goes** *Off → on*, *On → off* or *Any change*, for the jobs that act on a change. A number is on when it is not 0.
- **Read every** (50 to 10000 ms, 100 by default): the signals of one channel are read together, at the shortest time among them. Reads go on while an output action of the same channel runs: an input sees what a pulse switches on, for example when the PLC program copies an output action's tag to the tag an input reads. (No other output action comes between a value and its strobe.) For such a loop, make the pulse at least three times as long as the read time, and use *Off → on*: *Any change* acts twice per pulse. **Debounce** (0 to 5000 ms): a new value counts once it has lasted this long.
- **A sensor that switches faster than it is read is missed.** Let the PLC count the products and give the card the type *PLC counter*: the increase of the 16-bit counter since the last read is the number of products. The counter may wrap at 65535; an increase of more than 1000 between two reads is taken as the PLC resetting its counter and counts nothing.
- The **first read** of a signal is only its starting point: a start bit that is already on when the server starts does not start the line. Two jobs act at once: an alarm is raised when its value is on, and the batch number is taken as it is.
- Each card shows its **last value**, when it **last changed** and its **error**, once a second while Line setup is open. **Read now** reads the address once and shows the value, or why it could not be read; nothing the card would do is done.
- A value that cannot be read raises the alarm **Input cannot be read** (`plc.input_failed`) until it is read again. A PLC that cannot be reached raises the PLC connection alarm it always raised and is tried again at the channel's reconnect interval, not at every read; its cards show *PLC not connected*.
- A start, stop, reset or batch from a signal is written to the audit log as user `plc:<channel name>`, role `PLC`. A signal that changes nothing (a start for a running line, a reset when nothing was counted) writes nothing. A product sensor or a picture signal on a stopped line does nothing.

*Example*: a line with one code reader and a photo sensor wired to the PLC. Add a *Product sensor* card on the PLC's product counter (`R10`, *PLC counter*), a *Start the line* card on the operator's start bit and a *Set the batch number* card on the register that holds the work order. Switch **Sync** on: each product the PLC counts is paired with the code the reader saw, counted once, recorded with the batch and sent.

#### Trigger inspection (one picture per trigger)

For parts that stand still when they are inspected (an indexing machine, a rotary table), set the vision camera's **Count mode** to *One picture per trigger* (its card, **Counting**). The camera then tracks nothing and has no count lines. Each trigger takes the camera's next picture and makes **one** product of it:

- a class ticked under **Defects to reject** is found (or one named like a defect, with that switch on): **rejected**;
- else a class ticked under **Products to count** is found (or anything at all, when nothing is ticked there): **good**;
- nothing is found: **When nothing is found** decides, *Ignore* (no product), *Reject* (reason `nothing_detected`, PLC reason code 6) or *Good*.

The product is counted, recorded and sent like a tracked one and fires the same cards; with Sync or joined cameras it is paired and joined in the same way. A trigger is:

- an input with the action *Take a picture* whose trigger is ticked on the camera's card;
- `POST /api/v1/lines/{line_id}/trigger` (every camera of the line in trigger mode, or `{"camera_id": "..."}` for one);
- `POST /api/v1/control/trigger/{camera_id}`, which answers as it always did and now also makes the product for a camera in trigger mode.

When the system takes the picture, the camera's model runs only on that picture, not on every frame; its video shows WAITING FOR TRIGGER and no boxes. On a trigger the server waits the card's Picture delay, then takes the first frame that arrives after that moment (an industrial camera on Software trigger is fired then). The model then has 10 seconds for that picture; it is run once on a black picture when it is loaded or its line starts, so the first trigger does not wait for a cold model. When no picture comes within 2 seconds after the delay, the camera is not connected, or the model does not finish in time, the trigger still gets one answer: a product rejected with the reason *no picture* (PLC reason code 10), and the alarm **A trigger got no picture** (`camera.picture_missing`) until the camera's next picture. A trigger is refused, and makes nothing, while the line is stopped (also when it stops while the trigger waits) or the camera's model is not loaded. Two triggers at once on one camera take two pictures. The video of a camera in trigger mode shows no count lines.

#### Triggered industrial cameras (GigE Vision, USB3 Vision)

> **Not yet run on a real camera.** This part was built and tested against a stand-in camera. Before a first installation, work through [docs/real-life-tests/triggered-cameras.md](docs/real-life-tests/triggered-cameras.md) on a desk.

An industrial camera connects through the GenICam standard, so one driver covers GigE Vision and USB3 Vision cameras of every maker that follows it. It runs freely like a network camera, or takes one picture per trigger.

**Install.** `pip install -r requirements-industrial.txt`, and the camera maker's SDK, which brings the GenTL producer file (`.cti`) and sets `GENICAM_GENTL64_PATH`. `GENTL_CTI_PATH` in `.env` names the folders or files yourself; several makers' producers are loaded together, so cameras of several makers work at once. The server runs without any of this: only industrial cameras need it. On Windows the server must run natively for these cameras (Docker Desktop cannot reach them). On Linux in Docker: host networking, the maker's SDK folder mounted into the container, and `GENTL_CTI_PATH` set to it; this is not built into the image.

**Add one.** Line setup, **Add camera**, **Scan industrial cameras**, **Add to the camera list**. The camera is saved under its serial number. API: `GET /api/v1/cameras/discover/gige` (503 says what to install), then `POST /api/v1/cameras` with `type: "gige"` and `source` = the serial number.

**Its settings** are on the camera's card under **Image** (`settings` in the API). They are written to the connected camera when saved, without a reconnect.

| Setting | Values | |
|---|---|---|
| Trigger `trigger_mode` | `off`, `hardware`, `software` | Off: runs freely. Hardware: a signal on the camera's own input takes each picture. Software: the server takes each picture. |
| Trigger input `trigger_line` | such as `Line0`, `Line1` | Hardware only. The card offers the connected camera's own inputs. |
| Edge `trigger_edge` | `rising`, `falling` | Hardware only. |
| Trigger delay `trigger_delay_us` | 0 to 10,000,000 µs | From the trigger to the exposure. |
| Exposure `exposure_us` | 10 to 10,000,000 µs, or empty | Empty: the camera keeps its own. |
| Gain `gain_db` | 0 to 48 dB, or empty | Empty: the camera keeps its own. |
| Strobe output `strobe_line` | one of the camera's lines, or empty | On while the sensor is exposed, for a light. |
| Stream driver `stream_driver` | one of the drivers the maker's producer offers, or empty | How the pictures reach the server. Empty: the maker's default. With pylon, a camera simulated on this computer needs `SocketDriver`: pylon's GigE filter driver never sees pictures the computer sends to itself. Set before the pictures start; a change restarts them. |

A setting the camera refuses does not stop it connecting; the card lists it. On **Software** trigger the card has a **Software trigger** button: one picture now, to see that the camera answers (it shows how long the picture took); nothing is inspected, counted or sent. It is refused while the camera's line is running (the line's triggers take its pictures) and for a camera on Hardware trigger. API: `POST /api/v1/cameras/{id}/trigger` (Supervisor), 409 with the reason, 504 when no picture came within 2 seconds. A camera that refuses its trigger runs freely and says so, so that its pictures are never counted one product each by mistake.

**The Trigger follows the line's camera card.** When a line is saved, the server sets the Trigger of each of its vision cameras that is an industrial camera to what its card asks, only when it differs, as the camera's Settings would. A card with Count mode *One picture per trigger* controls the Trigger: Picture taken by *Camera trigger* is **Hardware**, *System trigger* **Software**. A card saved without a picture source follows the camera's Trigger (Hardware stays Hardware). Any other vision card leaves the Trigger as it is (a tracking camera on Hardware, a code reader that reads "When an input asks"), except **Software** that nothing on the card triggers, which is switched **Off**. A QR reader keeps its own Trigger. A camera that cannot be set does not stop the save: the answer's `warning` says "Camera 2's trigger mode could not be set: ...". *Camera trigger* on a camera that is not an industrial camera is refused (422). For a camera that a card with *One picture per trigger* controls, the camera list and `GET /api/v1/cameras/{id}` give the mode as `line_trigger_mode` (null when no card controls it), the Trigger is shown read-only ("Set on the line's camera card (Line setup)") and a `PUT` or `PATCH /api/v1/cameras/{id}` that sets another `trigger_mode` is refused (409). Only the mode is locked: the input, edge and delay of a Hardware trigger stay in the camera's Settings.

**How it is wired.**

```
Hardware trigger                                    Software trigger
sensor or PLC output ──wire──> camera trigger input  sensor ──> PLC input ──> PLC bit ──network──> server
camera strobe output ──wire──> light (optional)      server ──camera cable (trigger command)──> camera
camera ──GigE or USB3 cable──> server                camera ──GigE or USB3 cable──> server
server ──network──> PLC (reject pulse, as before)    server ──network──> PLC (reject pulse, as before)
```

- The camera's input is usually opto-isolated: the signal goes to the input pin and the signal's 0 V to the camera's I/O ground. Check the voltage range in the camera's manual.
- One sensor can go to the camera's input **and** to a PLC input. The camera then takes the picture; the PLC uses its copy for its own timing. Do not also add a *Take a picture* or *Product sensor* input for that sensor: the product would be counted twice.
- Hardware trigger is exact to microseconds and is the one for **moving** parts. Software trigger is late by the PLC's read time (50 ms or more) and the network, and suits parts that **stand still**.
- The result is known one picture transfer and one model run after the trigger. A reject gate's travel delay must be longer than that. A product's time is the time its picture arrived at the server.

**What a picture means** is the line's choice, on the same card. The camera's trigger decides *when* a picture is taken:

| Camera trigger | Count mode: moving products | Count mode: one picture per trigger | Read codes: continuously or on a wire line | Read codes: when an input asks |
|---|---|---|---|---|
| **Off** | as any camera | an input or the API takes the stream's next picture | as any camera | an input takes a fresh picture |
| **Hardware** | the newest picture, like a video (for a camera triggered by an encoder or a clock) | **every picture is one product**; no input | the newest picture, like a video (continuously: only shown, with a warning) | **every picture is read once**; no input |
| **Software** | warning: nothing takes its pictures | an input or the API triggers the camera, and **that picture is the product** | on a wire line the crossing triggers the camera; continuously gives a warning | an input triggers the camera and **that picture is read** (up to 3 pictures while no code reads) |

With hardware trigger and "every picture", no picture is skipped: up to 64 wait while the model is busy and are inspected in the order taken. When more than 64 wait, the oldest is dropped, the alarm **Camera pictures arrive faster than they are inspected** (`camera.trigger_overrun`) is raised, and the card says how many were lost. A picture taken while the line is stopped is shown, not inspected and never counted later. A input that asks a hardware-triggered camera for a picture is not obeyed; the card says so and the line warns about it.

**Trigger notice.** A missed or double hardware trigger cannot be seen. When a PLC or robot waits for each answer, give the camera's card (Picture taken by: Camera trigger) a **trigger notice**: the *Take a picture* input with that number then tells the server that a picture is coming, and is obeyed (it answers `"status": "expecting"`). A notice and a picture at most **Wait for the picture** apart (50-10000 ms, default 1000), in either order, are one product: made from that picture, with the notice's trigger number, product sequence and result handshake request. Only paired pictures are inspected. A notice whose picture does not come in that time is a product rejected with the reason *no picture* and the alarm `camera.picture_missing`; this also happens while the camera is disconnected. A picture that no notice claims is not inspected: it counts as *late* (just after a notice went missing) or *extra*, and 3 in a row raise **Camera pictures without a trigger notice** (`camera.picture_unpaired`) until the next paired picture. Pairing does not wait for the model: paired pictures wait for it in order (up to 64; beyond that the oldest is answered as *no picture*). A notice's time is when its input's edge was seen, even when reading the product sequence takes longer than the wait. When the line stops, the waiting notices and pictures are dropped and nothing is made of them. When Wait for the picture is changed while the line runs, each waiting notice is answered as *no picture* at once; the waiting pictures are counted extra. Keep the wait shorter than the time between two products.

A triggered camera can be silent for hours without an alarm. It is asked every 5 seconds whether it is still there; when it stops answering, **Camera stalled** is raised and the server opens it again by itself, with its trigger settings.

**Limits.** Level triggers, pulse-width (bulb) exposure, the trigger divider, CoaXPress and PTP-timed triggers are not built. The Line dashboard's camera tile shows the last picture as a still, and nothing before the first trigger (the card on Line setup says "waiting for a trigger"). On Software trigger, a camera that both counts per trigger and reads codes on a signal takes two pictures per signal. Clearing the strobe output does not switch the camera's line back until the camera is powered off and on.

**Without a camera.** `GENTL_CTI_PATH=simulator` gives two stand-in cameras (a picture every 2 seconds on Hardware, one per trigger on Software) to learn the screens with. `python "test codes/industrial_camera_check.py"` lists the real cameras the server would find and prints what one offers.

#### Trigger numbers: which input takes which camera's picture

An input with the action *Take a picture* is a **trigger**. It has a **trigger number** (1 to 99, the next free one by default) and names no camera. A camera that takes one picture per trigger chooses its triggers on **its own card**: under **Counting** when its Count mode is *One picture per trigger*, under **Read codes** when it reads codes *When an input asks*. Tick one trigger or several.

- Several cameras can tick the same trigger: one signal then takes a picture with all of them at once.
- One camera can tick several triggers: each of them takes its picture.
- A product's message and a code picture's record carry `trigger_no`, the trigger that took the picture.
- `POST /api/v1/lines/{id}/trigger` with `{"trigger_no": 2}` fires trigger 2 as its signal would. Without a body it triggers every vision camera in trigger mode, as before.
- The line warns about a trigger no camera ticked, a ticked trigger no input has, and a camera that reads codes on an input with no trigger ticked.
- An input saved before this (it named its camera itself) keeps working, and becomes a tick on that camera the next time the line is saved. API clients may still send `camera_id` on the input.
- A camera on **Hardware** trigger needs no tick: it takes its own pictures.

#### Connections: controllers, network cameras, OPC UA certificates

**Names.** The Connections page calls a PLC channel a **Controller**; Line setup calls its two PLC steps **Output actions** (what the line writes to a controller) and **Inputs** (what it reads from one). The API paths and setting names are unchanged (`/plc/actions`, `plc_inputs`, `protocol: "plc"`).

**Network camera.** Its **Camera type** is *IP camera* or *GigE Vision*.

- *IP camera*: the stream URL (RTSP, an MJPEG stream over HTTP, or a snapshot URL), an optional user name and password (saved inside the URL), the RTSP transport, the picture size and the buffer size. These three now reach the camera when the card is saved with them; before, they were stored and never used. A new camera keeps the stream's own picture size. The camera's own card on Line setup (Image) changes the same settings.
- *GigE Vision*: the camera's serial number. **Scan** lists the cameras found; **Use this camera** fills it in. **Test** looks for that serial number. API: `camera_kind: "gige"` and `source` = the serial number on a `protocol: "ipcam"` channel.
- One camera, one channel: a second channel with the same serial number is refused and names the first (a double click on **Save** made two before 2026-10-14; the button is now off while a save is on its way). Scan says **In use:** and the channel's name. A camera that is in the camera list without a channel (for example one left by an older version) is taken over by the new channel: it keeps its id, settings and place on its line. Deleting a channel deletes its camera, and every copy with the same serial number, so the camera is free to add again. The scan API gives `channel` (the channel's name, or null) beside `in_use`.

**OPC UA addresses by name.** On a controller that speaks OPC UA, the address of an output action or an input is the tag's name as the PLC shows it: `Tag_1`, or `DB1.Speed` for a member of a data block. The server looks the name up once per connection and uses the tag's full NodeId from then on:

- on a Siemens S7-1200/1500, `Tag_1` is `ns=3;s="Tag_1"`: the PLC's own namespace, and the name in double quotes (`DB1.Speed` is `ns=3;s="DB1"."Speed"`);
- on other servers, the same name without quotes in the server's own namespace;
- on a server whose nodes are numbered, the name is searched for from the Objects folder.

The result of **Test** and of **Read now** shows the NodeId that was used. A full NodeId still works as typed. One typed in the wrong form (`ns=2;s=Tag_1` on a Siemens PLC) is put right when the server does not know it. A name that two namespaces have is refused, with both NodeIds named. A name the server does not have is looked for again after 10 seconds. Checked by **reading** `Tag_1` and `Tag_2` from an S7-1500 (TIA Portal) on 2026-10-13; writing by name was not run on a PLC.

**OPC UA with a Security Policy.** A controller on OPC UA with a policy other than *None* needs a client certificate and its private key. The form shows **Client certificate**, **Private key** and **Server certificate (optional)**, each with **Upload**. A file is checked when it is uploaded (a certificate must be a certificate; a key must load without a password) and kept in `certs/opcua` on the server; the key is never sent back. Saving the channel checks that the key belongs to the certificate. API: `GET /api/v1/plc/opcua/certs`, `POST /api/v1/plc/opcua/certs/upload` (`file`, `kind` = `client_cert`, `private_key` or `server_cert`), then `opcua_cert_file`, `opcua_key_file` and `opcua_server_cert_file` on the channel. Not run against a real OPC UA server with security on; the stored files are read back with the OPC UA library in the tests. In Docker, mount `certs` as a volume or the files are lost when the container is rebuilt.

#### Batch number

A line has one **batch** (work order) number at a time, up to 64 characters. It is set on the **Line dashboard** (the **Batch** field beside the line's state: a Supervisor types it and presses **Set**, and an empty field clears it; everyone else sees it), with `PUT /api/v1/lines/{line_id}/batch` (`{"batch": "WO-2026-118"}`), or by an input with the action *Set the batch number*. Every change is written to the audit log, and the line keeps its batch over a restart.

From then on everything the line reports carries it: `batch` in its messages (pick **Batch** in a send card, or `{batch}` in a text message), the **Batch** column and filter of the Production records, the Sparkplug tag `Line/Batch`, and the PLC value *Batch number*. A line without a batch sends its messages exactly as before, without the key.

A batch read from a PLC is taken as text: `1001.0` becomes `1001`. One that is longer than 64 characters or holds a control character is refused, not cut short (a cut batch would be a wrong batch in the records), and the input shows why.

#### Product sequence, result handshake and sorting verification

For a line where the PLC stops each product for inspection and numbers it (a carton line). All three are optional; a line without them works as before. Set them on **Line setup**, under **Product sequence and result handshake** (inputs are chosen from the line's saved inputs) and on a code reader's card (**Sorting verification**).

**Product sequence.** Choose the input that holds the product's sequence number (`sequence_input_id`, any data type, for example a UINT `ProductSequence`). Each time a *Take a picture* input fires (or `POST /api/v1/lines/{line_id}/trigger` with `trigger_no`), the server reads it **once, now** (not the last polled value: the PLC sets the number and the request in the same scan) and the number travels with that request into the product: each product keeps its own number even when the PLC moves on before the result. A product made without a trigger (a moving line) takes the input's value of that moment. When the input cannot be read, the product has no number. The number is in the product's message and PLC event (`sequence`), the value name `sequence` (output action values, formulas, only-when rules, product checks), the text placeholder `{sequence}`, the send card field **Product sequence**, the product record (`details.sequence`), the CSV/XLSX export column `sequence` and the Line dashboard's reads.

**Result handshake** (`handshake`: `enabled`, `capture_input_id`, `ack_input_id`, `result_timeout_ms` 100 to 60000, default 3000, `ack_timeout_ms` 100 to 60000, default 5000, `on_timeout` `reject` or `fault`). The capture input is one of the line's *Take a picture* inputs; the acknowledge input is another input (for example *Only fires cards*). The acknowledge input's own **edge** says what acknowledges: *Off → on* (the default), or *On → off* for a PLC that drops its capture request as the acknowledge (a second input on the request's own address). The line goes *idle* → *waiting for the result* (the capture fired; its sequence is noted) → *result sent* (the product's one result went out and fired its output actions) → *idle* when the acknowledge input goes on. Your own output actions set and reset the PLC's flags, for example SET `InspectionDone` / `PassRequest` / `RejectRequest` on *Product crossed line: any / good / rejected*, and RESET each of them on *Input changed: on* of `ResultAck`.

- No result within the result timeout: *reject* makes one rejected product (reason `inspection_timeout`, reject reason code 8), counted once and recorded, so the reject actions fire; *fault* raises the alarm `line.inspection_timeout` and fires the trigger **Handshake fault**. Never a pass. A result that comes later for that request is not counted again (the handshake counts it as *late*). Both wait for the acknowledge, so the PLC acknowledges a fault the same way.
- No acknowledge within the ack timeout: alarm `line.ack_timeout` and the trigger **Handshake fault**; the alarm clears when the acknowledge comes.
- A new capture while the last result waits for its acknowledge (the PLC skipped it), or before the last result came: alarm `line.handshake_fault` and the trigger **Handshake fault**, then the new capture goes ahead. The alarm clears with the next acknowledge.
- A capture with the sequence that is still in the handshake is a duplicate: no picture, counted. An acknowledge with nothing to acknowledge is stale: ignored by the handshake, counted and logged (the acknowledge input's own output actions still fire: resetting flags that are off does no harm).
- After a server restart the handshake starts idle; flags the PLC holds stay set until the PLC drops them. When the PLC link drops while a result is awaited, the result timeout still runs and its rule applies; an acknowledge that cannot be read ends in the ack timeout alarm.
- `GET /api/v1/lines/{line_id}/handshake` (Monitoring) answers `state`, `sequence`, `since`, `last_result`, `stale_acks`, `timeouts`, `ack_timeouts`, `duplicates`, `late`, `last_error` and `settings`; the Line dashboard shows it. With the handshake on, Sync pairs a capture's code with the product of the same request.

**Sorting verification (Camera 3).** On a code reader's card, **Sorting verification** makes it watch the *accepted* or the *rejected* outfeed (`sorting_lane`; one camera per outfeed). Its reads, triggered or *Continuously* (it reports, it never decides, so it verifies Continuously too; keep its hold time shorter than the gap between two products with the same code), never make a product, never count, never pair and fire no code cards. Each read is matched to the **oldest** product with that whole code that is not verified yet (the line remembers its last 200 products that had a code): a good product belongs in the accepted outfeed, a reject in the rejected one.

- Match: the product is verified; the trigger **Sorting verified** fires.
- Mismatch: alarm `line.sorting_mismatch` (code, sequence, expected and seen outfeed), the trigger **Sorting mismatch**, and a production record of kind `verification` (result reject, reason `sorting_mismatch`, `details.expected_lane` / `seen_lane` / `sequence`; filter `kind=verification`). The alarm clears when the handshake's acknowledge input goes on, and when the line's counters are reset.
- A code with no product waiting: counted as *unmatched* (event `SORTING_UNMATCHED` on the event bus), no alarm. A product without a code (no QR) cannot be verified. A product Camera 3 misses stays unverified, and the next product with the same code is matched to it: reset the counters to start the memory again.
- The Line dashboard shows *verified*, *wrong outfeed* and *unmatched* (also `sorting` in the line summary and in `GET /api/v1/lines/{line_id}/qr/recent`).
- To tell the PLC: an output action SET `VerificationFault` on **Sorting mismatch**, and one RESET `VerificationFault` on *Input changed: on* of `ResultAck`.

#### Models, product lists and the API

**AI models**: each vision camera runs the model chosen for it on Line setup, so several models run at the same time; cameras that choose the same model share one loaded copy. On the **AI models** page a model shows as *Active* while at least one camera runs it, with the line and camera under **Used by**; there is no Activate button, and a model that is in use cannot be deleted. A model that cannot be loaded (a missing or damaged file, or no memory left on the GPU) raises the alarm *Camera has no model it can run* for each camera of a running line that needs it; Line setup shows the reason in that camera's card, and nothing is detected on that camera until it loads. A class name saved before the lists were picked from the model, and which the model does not have, is shown as *not in this model* with a warning. All loaded models share the machine's one GPU: on a small GPU, check the alarms after adding a model.

Calls written for the one active model of version 1 keep working, where that server's one camera is now Line 1's counting camera: `POST /api/v1/models/{id}/activate` picks the model for Line 1's counting camera (the same as choosing it on Line setup), `GET /api/v1/models/active` returns that model, and the detect calls (`POST /api/v1/vision/detect`, `/vision/detect/camera/{id}`) take an optional `?model_id=`; without it they run the camera's own model, else the model of Line 1's counting camera, and fail with a message when there is none. `GET /api/v1/models` gives each model's `is_active`, `used_by`, `loaded` and `load_error`. A model file left in `model_store/` without being uploaded or registered is no longer loaded by itself.

**Product lists**: **Products** page, or the API. There are up to four lists; the page shows one at a time, chosen in **List shown**, and each camera that reads codes is set to one list on Line setup. CSV files need a header row `code,name` (`description` optional). **Import CSV as a new list** makes a new list named after the file (refused when there are four); **Replace contents** makes the list that is shown hold exactly the rows of a file and keeps its id and name, so the cameras set to it keep working; a list that a camera uses cannot be deleted. The same code may be in more than one list. An MES or ERP system can keep a list current with `POST /api/v1/products/lists/{list_id}/replace` and an API key with `configuration:write` (`GET /api/v1/products/lists` gives the ids).

**Code format.** A list's **Code format** button says how its codes are built, so one code can carry the product **and** its batch:
- *Whole code* (the default): the whole code is the product, as before.
- *Parts with a separator*: for example list "Cartons" with separator `;`, product ID part 1 and batch part 2. The code `P-100;B-2026-07` finds product `P-100` and the item carries batch `B-2026-07`. Each part is trimmed; the list holds the product IDs (`P-100`), so CSV files do not change.
- *GS1*: the `(01)` GTIN (14 digits) finds the product and `(10)` is the batch; both the readable form `(01)09501101530003(10)L-2026-07` and the raw form with GS separators are read, and other parts such as `(17)` are skipped.

A code that does not fit the format counts as an unknown code: *Accept only listed codes* rejects it (`code_not_in_list`), and the message and the record say why in `code_problem` (`no separator`, `no product part`, `no batch part`, `empty product ID`, `not GS1`, `no (01) part`, `unknown GS1 part`). A batch longer than 64 characters or with a control character is dropped (`batch not allowed`); the product is still found. **Try a code** in the dialog (`POST /api/v1/products/lists/{list_id}/code/check`, also with an unsaved `code_format`) shows the product ID, the batch and the product found. Each item keeps **its own batch**: it replaces the line's batch for that item in its message, its PLC event, the value `batch` (rules, formulas, writes) and the records' batch column; an item whose code has no batch keeps the line's. The value `product_id` (and `{product_id}` in a text message) is the product ID the code holds; a message carries `product_id` only where it is not the whole code, so a list that reads whole codes sends the messages it sent. The output action value *The code read* still writes the whole code. A code reader can also set **The code's batch sets the line's batch**: a listed product whose code holds another batch makes it the line's batch, written to the audit log as `camera:<name>` (codes only shown, and unknown codes, never change it); the line warns when the reader's list has no batch part.

**Product data**: each list can have up to 20 fields of its own (**Fields** on the Products page), each a number, text, or yes or no. A product gets a value for each field in its **Add** or **Edit** dialog, or from a CSV file, where the columns after `code,name,description` are fields:

```
code,name,description,Lane,Recipe,Expected class
J-1,Apple juice,,1,R-1,apple
J-2,Orange juice,,2,R-2,orange
J-3,Grape juice,,3,R-3,grape
```

- **Import CSV as a new list** makes one field per extra column. The type comes from the cells: all numbers make a number field, all `yes` / `no` / `true` / `false` / `1` / `0` a yes-or-no field, anything else text; a column with a leading zero (`0042`) or a `+` (`+44`) stays text, so nothing is lost. An empty cell leaves the product without a value (not 0, not "no"). A column that cannot be a field (past 20 fields, a header that comes again, or a cell no field can hold, such as a line break) is left out, and the answer lists it in `ignored_columns`.
- **Export CSV** writes the fields' keys as the headers, so the file reads back unchanged.
- **Replace contents** matches a column to a field by its key or its label (any case) and refuses a column that is no field of the list. A list without fields reads only `code`, `name` and `description`, as before, and lists the other columns in `ignored_columns`. A field the file has no column for keeps each product's value, so an older file without the data columns wipes nothing.
- A field's **key** (`lane`) names it everywhere (`product.lane`) and never changes once saved; its label can. Deleting a field, or changing its type, removes the values that no longer fit and says how many.

When a code from a list is read, its product goes with the item. The product's message, its PLC event, a code read's message and the record carry `product`: its `code`, `name`, `list`, `list_id` and `fields` (the values at that moment). A JSON message can list the field `product`; a text message can use `{product.name}`, `{product.code}`, `{product.list}` and `{product.<key>}` (`{product.recipe}`). A code that is in no list has no `product`, and its placeholders are empty.

**API**: `GET /api/v1/lines` and `/lines/overview` list lines with their live figures; `POST /api/v1/lines`, `PUT`/`DELETE /api/v1/lines/{line_id}`, `POST .../start`, `.../stop` and `.../clone` change them (up to 8 `cameras`; each vision camera carries its `model_id`, `expected_classes`, `defect_classes`, `confidence`, `name_based_defects`, its count lines `line1_position`, `line2_position`, `orientation` (`horizontal`: lines across the picture, `vertical`: lines down it), `direction` (`forward` from line A to B, `backward`, or `both`), `tracking`, and for a camera that is not the counting camera its `station`, `own` or `join`, with `join_offset_ms` (-60000 to 60000), `join_window_ms` (50 to 10000, default 500) and `join_missing` (`reject` or `ignore`, the default) for `join`; a client that leaves one of these out keeps its saved value, and one sent empty goes back to its default); a vision camera also carries `count_mode` (`track`, the default, or `trigger`) and, in trigger mode, `no_product` (`ignore`, `reject` or `good`) and the picture keys `picture_source` (`system`, the default, or `camera`), `picture_delay_ms` (0 to 5000), `notice_trigger` (1 to 99 or `null`) and `picture_wait_ms` (50 to 10000, default 1000), and a camera that reads codes can have `qr_trigger` `signal`. A line's `plc_inputs` are its inputs, sent whole with `PUT /api/v1/lines/{line_id}` (a body without the key keeps them): `id`, `name`, `enabled`, `plc_endpoint_id`, `address`, `data_type` (`auto`, `bool`, `int16`, `uint16`, `int32`, `real`, `string`, `counter`), `poll_ms`, `edge` (`rising`, `falling`, `change`), `debounce_ms`, `action` (`start_line`, `stop_line`, `run_level`, `reset_counters`, `product_sensor`, `capture`, `set_batch`, `confirm_card`, `alarm`), `camera_id` for `capture`, and `alarm_text` and `alarm_severity` for `alarm`. `GET .../plc-inputs/status` gives each card's `value`, `changed_at`, `last_read_at`, `read_count` and `error`; `POST .../plc-inputs/{input_id}/read` reads one address now (with `{"input": {...}}` for a card that is not saved yet). `PUT .../batch` sets the line's batch number, and `POST .../trigger` triggers its cameras in trigger mode. Card ids (output actions, send cards, inputs) use letters, digits and `_ . : -`, up to 64 characters; a save with another id is refused with 422. An output action card carries `confirm_input_id` (an input with the action `confirm_card`) and `confirm_timeout_ms`; its status can be `confirmed` or `not_confirmed`. `GET .../qr/recent` gives the latest reads and the last picture's details, `GET .../qr/capture` the last picture (JPEG) and `POST .../qr/capture` takes a test picture. The counting, output action, alarm, health and metrics endpoints take an optional `?line_id=`. Events sent to MQTT, TCP and webhooks gain `line_id`, `line_name` and `camera_id`, plus `qr_code`, `qr_status` and `product_name` for synced products; a product's event also carries `reject_reason` (`vision_class`, `code_not_in_list`, `code_in_reject_list`, `no_code`, `station_no_result`, `nothing_detected`, `product_check`, `inspection_timeout` or `no_picture`, with `product_check` naming the check) and, while the line has one, its `batch`, and on a line with joined cameras `stations` and `reject_camera_id` (see *Several cameras on one product*). What a line sends is on its send cards: `GET /api/v1/send/actions`, `POST /api/v1/send/actions/batch` and `POST /api/v1/send/actions/{id}/test` (with `?line_id=`), and `GET /api/v1/send/fields` for what a message can contain (`fields`) and the placeholders of a text message (`placeholders`); a card's `format` is `json` or `text` and its `template` holds the text; code reads go out as `QR_CODE_READ` events from a card with a code trigger. The product list calls are `GET /api/v1/products/lists`, `POST /api/v1/products/import` (a new list), `POST /api/v1/products/lists/{list_id}/replace`, and `?list_id=` on `GET /api/v1/products` and `/products/export`; `PUT /api/v1/products/lists/{list_id}` takes `name`, `fields` (`[{"key", "label", "type"}]`, `type` `number`, `text` or `yes_no`; the answer's `dropped` says how many values were removed) and / or `code_format` (`{"mode": "whole"}`, `{"mode": "split", "separator", "product_part", "batch_part"}` or `{"mode": "gs1"}`), and `POST .../code/check` tries a code; `POST /api/v1/products` and `PUT /api/v1/products/{id}` take `data` (`{key: value}`; left out of a `PUT`, the values are kept). Prometheus metrics gain `vision_server_line_*` series with a `line` label. Flows can be limited to one line with a `production_line` value on the trigger node.

Nothing has run against real PLCs yet: start the first plant trial with one line on a spare PLC or a simulator. Reading inputs was run against the Modbus TCP simulator in `test codes/plc_simulator.py` (a coil started a line and a counter register counted its products) and, for every protocol, against small stand-in PLCs in the tests; no protocol's read has met a real PLC.

### Production records and export

Every product a line decides (good or reject, with its reason, class, confidence and paired code) and every code read that is not part of a product is stored in the `product_records` table. Products seen by an *own station* camera are stored too but marked as not in the line totals (`counted` false). A joined camera's results are in its product's `details.stations`.

- **Writing never slows the line down.** The cameras' threads only queue a row; a background task writes the queue once a second (or as soon as 500 rows wait) in one transaction. If the database cannot keep up, at most `RECORDS_QUEUE_LIMIT` rows (default 100000) wait; past that the oldest are dropped and the alarm **records.dropped** is raised. When writes fail three times in a row the alarm **records.write_failed** is raised; the rows are kept and retried every second. Rows still waiting at shutdown are written before the database closes.
- **Retention.** Rows older than `RECORDS_RETENTION_DAYS` (default 90; 0 keeps them for ever) are deleted once an hour, 5000 at a time, so the database is never locked for long. Count about 400 bytes per row with its indexes: a line counting one product a second makes about 7.8 million rows (some 3 GB) in 90 days.
- **Counters survive a restart.** Each line keeps `counts_reset_at` (when its counters were last reset) in its entry in `data/system_state.json`, Line 1 too. At startup each line's counters, and each own station's, are rebuilt from the records since then. **Reset counts** (the dashboard, `POST /api/v1/counting/reset` or a Sparkplug command) sets it to now; resetting single classes is kept too (`counts_reset_classes`). The upgrade to this version sets it to the upgrade time, so the counters start from 0 once and are kept from then on. Products per minute is not kept (it is a one-minute window).

**Production records page** (sidebar, under *Run*; every signed-in user): pick the line (or *All lines*), **From** and **To** (in the browser's time zone) or a quick range (*Last hour*, *This shift* = last 8 hours, *Today*, *Yesterday*, *Last 7 days*; these follow the clock while the page is open), and filter by result, kind, camera, batch and code. The tiles show the line totals of the range, then products per hour (per day for ranges over 48 hours), rejects by type, and the records, 50 per page, newest first. **Export CSV** and **Export Excel** download the same range and filters.

**API** (Operator level; API keys need the `records:read` scope). Every call takes `start` and `end` (ISO 8601 with a time zone, e.g. `2026-10-09T06:00:00Z`; `end` is not included; at most 366 days apart) and the filters `line_id` (empty = every line), `result` (`good` / `reject`), `kind` (`product` / `code`), `batch`, `code` (contains), `camera_id` and `counted`.

| Call | Returns |
| --- | --- |
| `GET /api/v1/records?limit=100&offset=0` | `{total, rows}`, newest first; `limit` up to 1000. |
| `GET /api/v1/records/summary?bucket=hour&tz=Europe/Berlin` | `totals` (`total`, `good`, `reject`, `yield`), `by_class`, `by_reject_reason`, `by_camera`, `codes` (rows per code status) and `buckets` per hour or day in `tz`. The totals count the line totals' products (`counted`) unless `camera_id` or `counted` is given. |
| `GET /api/v1/records/export?format=csv&tz=Europe/Berlin` | A CSV file (UTF-8 with a byte order mark): the time in `tz` and in UTC, then every column. Text that a spreadsheet would run as a formula starts with `'`. Read and sent in chunks, so any range downloads without filling the server's memory. |
| `GET /api/v1/records/export?format=xlsx&tz=…` | An Excel workbook: a **Records** sheet (times as Excel dates, numbers as numbers) and a **Summary** sheet (the summary above). An Excel sheet holds 1,048,575 rows: a larger range is refused with `413`; export it as CSV or choose a shorter range. |

An unknown `tz` falls back to UTC; the response then says so in its `X-Records-Timezone-Note` header. The file name is `records_<line>_<from>_<to>.<csv|xlsx>`. Columns: `line_id`, `line_name`, `camera_id`, `camera_name`, `kind`, `counted`, `result`, `reject_reason`, `class_name`, `confidence`, `track_id`, `code`, `code_format`, `code_status` (`known` / `unknown` / `no_read`), `product_name`, `product_list_id`, `batch` (filled once the line has a batch number), `reject_camera_id`, `stations` (JSON), `product_data` (the product's values when it passed, `key=value; key=value`), `product_check` (the product check that rejected it) and `id`.

### Sparkplug B (Ignition and other SCADA hosts)

Sparkplug B is the plant standard on top of MQTT: fixed topic names, binary payloads, and birth and death messages. A host such as Ignition (with the Cirrus Link MQTT Engine module) then finds the tags by itself and knows when the device behind them is offline. With it switched on for an MQTT channel, this server is an **edge node** on that channel's broker and every production line is one of its **devices**. Send cards on the same channel keep working; Sparkplug uses a connection of its own.

**Setup.** Connections, edit the MQTT channel, section **Sparkplug B**:

| Setting | Meaning |
| --- | --- |
| Publish the production lines as Sparkplug B | On or off for this channel. |
| Group ID, Edge node ID | Where the lines appear in the host, for example `PlantA` and `VisionServer1`. No `/`, `+` or `#`. Two channels to the same broker cannot use the same pair. |
| Primary host ID | Optional. The host ID set in Ignition's MQTT Engine. The lines are then published only while that host reports itself online, and born again when it comes back. |
| Allow commands | Off by default. See **Commands** below. |
| Publish interval | 100 to 60000 ms, 1000 by default. Changed values are sent at most this often. |

In Ignition, point MQTT Engine at the same broker (and set the same Primary Host ID, if one is used). The lines appear under `Edge Nodes/<group>/<edge node>/<line name>`. The channel's card on the Connections page shows the node's state (publishing, waiting for the host, or not connected), and so does `GET /api/v1/telemetry/health` under `components.mqtt.channels[].sparkplug`.

**What each line publishes.**

| Tag | Type | |
| --- | --- | --- |
| `Line/Running`, `Line/Name` | Boolean, String | The line is started; its name. |
| `Line/Batch` | String | The line's batch number; empty while it has none. |
| `Counts/Inspected`, `Counts/Good`, `Counts/Rejected` | Int64 | The line's totals. |
| `Counts/Class/<class>` | Int64 | One per class the line's cameras are set to, and any other class that was counted. |
| `Rate/Products Per Minute`, `Quality/Yield Percent`, `Quality/Defect PPM` | Double | |
| `Last Product/Result`, `Class`, `Reject Reason`, `Code`, `Confidence` | String, Double | The latest product. |
| `Last Code/Text`, `Last Code/Status` | String | The latest code read: `known`, `unknown` or `no_read`. |
| `Cameras/<camera name>/Connected` | Boolean | One per camera of the line. |
| `Alarms/Active Count`, `Alarms/Active` | Int32, String | The line's active alarms; their codes, comma separated. |
| `Commands/Reset Counters` | Boolean | Always false; a host writes true. |

The node itself publishes `Node Control/Rebirth`, `Node Info/Software Version` and `bdSeq`.

- Only changed tags are sent. `Last Product` therefore shows the latest product of an interval, not every product; a send card reports every one.
- A line that is added, renamed or deleted is born or dies as a device; a renamed line is a new device. A class counted for the first time, or a camera added to a line, gives that line a new birth, because a tag has to be in the birth before data can be sent for it.
- After an outage of the broker the node is born again with the current totals. Messages are not buffered while the broker is unreachable; the counters are totals, so nothing is lost from them. After a restart of the server the counters carry on from where they were (see **Production records and export**), as on the dashboard.
- A rebirth request from the host (`Node Control/Rebirth`) is always answered.
- A server that is stopped or crashes is reported offline at once. One that loses power or its network is reported by the broker after about 20 seconds (the Sparkplug connection pings every 15).
- Class names are published in lower case, as the counters count them: a class set as `Bottle` is the tag `Counts/Class/bottle`.

**Commands.** With **Allow commands** on, a host can write `Line/Running` (true starts the line, false stops it, as the dashboard's buttons do) and `Commands/Reset Counters` = true. Each one is written to the audit log as user `sparkplug:<channel name>`, and the tag's real value is sent back at once, also when a write was refused. Anything else a host writes is ignored. Anyone who can publish to the broker can send these, so leave the switch off unless it is needed, and on a broker with logins per client give the host its own. The bundled broker has one login for every client: with the switch on, every device that holds it can start and stop the lines. A command that a broker kept as a retained message is not carried out.

Tried against Mosquitto, with the messages also read by Eclipse Tahu's own message definition. Not yet tried against Ignition itself: check the first connection there before relying on it.

### Tests and lint

```bash
pip install -r requirements.txt -r requirements-dev.txt
pytest
ruff check .
```

Tests use a temporary database and fake cameras, ONNX inference and PLCs, so no hardware is needed. GitHub Actions runs both, plus a Docker Compose build, start-up, health and clean-stop check, on every push and pull request.

Database migrations run during startup. For access outside a trusted isolated network, terminate TLS at a trusted reverse proxy and expose only HTTPS/WSS; the built-in development server does not configure TLS certificates. The API rate limit (`RATE_LIMIT_PER_SECOND`, per client address) needs the proxy to send `X-Forwarded-For` and uvicorn to trust it: set `FORWARDED_ALLOW_IPS` to the proxy's address in the server's environment (or pass `--forwarded-allow-ips`), otherwise every user behind the proxy shares one limit. In production, query-string WebSocket tokens are disabled. Browser clients should send the token using the `Sec-WebSocket-Protocol` values `industrial-vision-v1` and `bearer.<access-token>`; native clients may use an Authorization bearer header.
